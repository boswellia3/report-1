# report-1 "CVE-2026-31431の読解と報告"

## 概要
本リポジトリは、自身の活動報告をしたあと、Linuxカーネルにおける脆弱性CVE-2026-31431を、公開情報を元に技術的な内容の読解をカーネル内部の動作のレイヤーでc++寄りの概念モデルでまとめたものです。本リポジトリには悪用可能なコード（Exploit）は含まれていません。

## 脆弱性ステータス: 修正済み (Fixed)
本脆弱性はすでに修正済みです。影響を受けるシステムを使用している場合は、直ちに最新のセキュリティアップデートを適用してください。

## 対策と対応状況
各Linuxディストリビューションから修正済みカーネルが配布されています。
- **パッチ適用**: 各ディストリビューションのセキュリティ情報を確認し、修正済みカーネルへ更新してください。
- **緩和策**: アップデートが難しい環境では、脆弱なモジュール（`algif_aead`）の無効化を検討してください。

## 解説
最終的な目的は、/usr/bin/su というELF実行ファイルを読み取り専用で開き、その実行開始地点がファイル上のどこに対応するかを調べたうえで、Linuxカーネルの暗号APIである AF_ALG と splice() を使い、ディスク上のファイルそのものではなくページキャッシュ上の見え方を一時的に変えることです。
つまり、普通に /usr/bin/su を write() で書き換える話ではありません。/usr/bin/su は読み取り専用で開いているので、通常のVFSの書き込み経路なら権限チェックで弾かれます。今回の話の本質は、通常のファイル書き込みではなく、カーネル内部の暗号処理経路で「本来書き込み先にしてはいけないページキャッシュ」を dst、つまり出力先として扱ってしまったことです。
全体の流れを先に書くと、こうです。
/usr/bin/su を読み取り専用で開く
        ↓
ELFヘッダを読み、実行開始仮想アドレス e_entry を得る
        ↓
e_entry をファイルオフセット entry_foff に変換する
        ↓
AF_ALG ソケットを作り、AEAD暗号 authencesn を選ぶ
        ↓
splice() で /usr/bin/su の page cache を AF_ALG の入力側に持ち込む
        ↓
algif_aead の in-place 処理で src と dst が重なる
        ↓
authencesn が dst に hiseq 4バイトを書く
        ↓
dst が page cache を指していたので、page cache の4バイトが上書きされる
        ↓
その状態で execl() して /usr/bin/su を実行する
まず、open(TARGET, O_RDONLY) で /usr/bin/su を読み取り専用で開きます。
ここで大事なのは、O_RDONLY なので普通の意味では書き込みできないということです。つまり、このfdに対して普通に write() して /usr/bin/su を書き換えることはできません。
ただし、今回狙っているのはディスク上のファイルそのものではなく、カーネルがメモリ上に保持するページキャッシュです。ページキャッシュは、ディスク上のファイル内容をカーネルがRAM上に保持しておく仕組みです。ファイルを読むときも、実行するときも、このページキャッシュが関係します。
なお、open() した瞬間に必ず対象範囲のページキャッシュが全部できる、というより、open() によって対象ファイルを指すfdを得て、その後の pread()、splice()、exec などの処理でそのファイル内容がページキャッシュ経由で扱われる、という理解の方が正確です。
open() が成功すると、カーネルはそのファイルを操作するための番号、つまりファイルディスクリプタ tgtfd を返します。
次に、pread(tgtfd, &ehdr, sizeof(ehdr), 0) で /usr/bin/su の先頭からELFヘッダを読みます。ちなみに pread は positional read の略で、ファイルオフセットを指定して読む関数です。ここではオフセット 0 から読むので、ELFファイルの先頭にあるELFヘッダを読み取っています。
このELFヘッダの中にある e_entry が、実行開始地点、つまりエントリポイントを表します。
ただし、ここが少し罠です。ehdr.e_entry はファイル上の位置ではありません。これは実行時の仮想アドレスです。つまり、「ファイルの先頭から何バイト目か」というファイルオフセットではなく、「実行時の仮想メモリ上でどこから実行を始めるか」という値です。
だから、e_entry をそのまま使って、
/usr/bin/su の e_entry バイト目を書き換える
みたいなことはできません。仮想アドレスとファイルオフセットは別物だからです。
そこで vaddr_to_foff(tgtfd, ehdr.e_entry) を使います。vaddr_to_foff は virtual address to file offset、つまり仮想アドレスをファイルオフセットに変換する関数です。
この関数はELFのプログラムヘッダを読み、e_entry がどの PT_LOAD セグメントに含まれているかを調べます。PT_LOAD は、実行時にメモリへロードされるセグメントのことです。
対象の仮想アドレスがある PT_LOAD セグメント内にあれば、次の式でファイル上の位置に変換できます。
file_offset = p_offset + (vaddr - p_vaddr)
ここで、p_offset はそのセグメントがファイル上で始まる位置、p_vaddr はそのセグメントがメモリ上に配置される仮想アドレス、vaddr は変換したい仮想アドレスです。今回なら vaddr = ehdr.e_entry です。
つまり、
vaddr - p_vaddr
で、そのセグメントの先頭から何バイト進んだ位置かを出し、それをファイル上のセグメント先頭 p_offset に足しています。
イメージはこうです。
メモリ上:

p_vaddr                         e_entry
  |--------------------------------|
          vaddr - p_vaddr


ファイル上:

p_offset                        entry_foff
  |--------------------------------|
          同じだけ進む
これで、実行開始地点に対応するファイルオフセット entry_foff が得られます。
簡単にいうと、メモリの仮想アドレスを、副記憶装置上の保存位置、つまりファイルオフセットに変換しています。ここをやらないと、「実行開始地点を書き換えたい」と思っても、ファイル上のどこを狙えばいいのか分かりません。
次に、socket(AF_ALG, SOCK_SEQPACKET, 0) でLinuxカーネルの暗号APIとやり取りするためのソケットを作ります。ソケットというと普通はネットワーク通信のイメージが強いですが、Linuxではソケットをネットワーク以外のカーネル機能への入口として使うこともあります。AF_ALG はその一つで、カーネル暗号APIをユーザー空間から使うためのアドレスファミリです。
socket() の引数は、
socket(domain, type, protocol)
です。
第1引数の AF_ALG は、どのアドレスファミリ、つまりどの世界のソケットを作るかを指定しています。AF_INET ならIPv4通信、AF_INET6 ならIPv6通信、AF_UNIX なら同一マシン内通信、AF_ALG ならカーネル暗号APIの世界、という感じです。
だから AF_ALG を「入口」と呼ぶのは、socket(AF_ALG, ...) とした時点で、そのfdに対する bind()、sendmsg()、recv() などの操作が、カーネル暗号API側の処理として解釈されるからです。僕目線でも最初はプロトコル選択っぽく見えますが、正確にはプロトコルというより「どの通信ドメイン、どのaddress familyか」の選択です。
第2引数の SOCK_SEQPACKET は、順序付きパケット型ソケットを表します。SOCK_STREAM のような単なる連続バイト列ではなく、メッセージ境界、つまり1回ごとの処理単位を保つ形式です。AF_ALGでは「この1回分の暗号処理」という単位が大事なので、この形式が使われます。
第3引数の 0 は、特別なプロトコル指定をせず、デフォルトを使うという意味です。
つまり、
socket(AF_ALG, SOCK_SEQPACKET, 0)
は、
カーネル暗号APIの世界で、
順序付きパケット型のソケットを、
デフォルト指定で作る
という意味です。これで algfd が得られます。algfd は暗号APIとやり取りするための親ソケット、つまり暗号APIへの親窓口です。
次に、bind(algfd, ...) によって、どの種類の暗号を使うかを指定します。AF_ALGでは、bind() に struct sockaddr_alg を渡し、その中の salg_type と salg_name で暗号の種類と具体的なアルゴリズム名を指定します。
たとえば、
salg_type = "aead";
salg_name = "authencesn(hmac(sha256),cbc(aes))";
のように指定します。
ここで salg_type = "aead" は、AEAD系の暗号を使うという意味です。AEADは Authenticated Encryption with Associated Data の略で、認証付き暗号を表します。
そして salg_name = "authencesn(hmac(sha256),cbc(aes))" は、具体的にどのAEADアルゴリズムを使うかの名前です。これは、認証にHMAC-SHA256、暗号化にAES-CBCを使う構成です。
ここで重要なのは、AF_ALG、algif_aead、authencesn が同じものではないことです。
AF_ALG は、socket(AF_ALG, ...) に出てくるカーネル暗号APIへの入口です。
algif_aead は、ユーザーコードに直接出てくる引数名ではありません。salg_type = "aead" を指定した結果、カーネル内部で使われるAEAD用のAF_ALG実装です。ファイル名でいうと crypto/algif_aead.c みたいなやつで、AEAD用のドライバ、あるいはアダプタだと思うと分かりやすいです。これは暗号そのものというより、AF_ALGソケットから来た入力を受けて、カーネル暗号API用のrequestを作る側です。
authencesn は、salg_name で指定された実際の暗号処理エンジンです。つまり、algif_aead がAEAD requestを組み立て、そのrequestを authencesn に処理させる、という関係です。
まとめるとこうです。
AF_ALG
  = socket() の第1引数に出る
  = カーネル暗号APIへの入口

salg_type = "aead"
  = AEADカテゴリを選ぶ
  = 内部では algif_aead が担当になる

algif_aead
  = AF_ALGのAEAD用ドライバ/アダプタ
  = src/dst を持つrequestを組み立てる側

salg_name = "authencesn(...)"
  = 実際に使う暗号アルゴリズム名

authencesn
  = 実際に処理を行う暗号エンジン
次に、setsockopt(algfd, SOL_ALG, ALG_SET_KEY, keyblob, keylen) で暗号鍵を設定します。setsockopt は set socket option、つまりソケットのオプションを設定する関数です。SOL_ALG はAF_ALG用の設定レベル、ALG_SET_KEY は暗号アルゴリズムに鍵を設定する命令です。keyblob は鍵データのバイト列で、keylen はその長さです。
さらに、setsockopt(algfd, SOL_ALG, ALG_SET_AEAD_AUTHSIZE, &authsize, sizeof(authsize)) でAEADの認証タグサイズを設定します。ALG_SET_AEAD_AUTHSIZE はAEADのauthentication size、つまり認証タグのサイズを指定するためのオプションです。認証タグは、データが改ざんされていないかを確認するための値です。AEADでは復号時にこのタグが検証されます。
実際の1回分の暗号処理を行うときは、accept(algfd, NULL, 0) で処理用の子ソケットを作ります。
ネットワークの accept() は接続してきた相手を受け入れる操作ですが、AF_ALGでは、設定済みの親ソケット algfd から、1回分の暗号処理に使う子ソケットを作る操作だと考えると分かりやすいです。この子ソケットを opfd とします。
algfd
  = 暗号方式・鍵・認証タグサイズなどを持つ親窓口

opfd
  = 今回1回分の暗号処理を走らせる処理専用窓口
次に、sendmsg(opfd, ...) で暗号APIに処理条件を送ります。sendmsg() は通常のデータだけでなく、制御情報も送れる関数です。AF_ALGでは、暗号化か復号か、IVは何か、関連データ長はどれか、といった情報を送るために使います。
その後の splice(...) がかなり重要です。
splice() は、ユーザー空間を経由せずに、カーネル内部でfdからfdへデータを移動するシステムコールです。普通の read() / write() だと、データはいったんユーザープログラムのメモリにコピーされます。
普通の read() なら、イメージはこうです。
/usr/bin/su の page cache
        ↓ read()
ユーザー空間の malloc バッファ
この場合、ユーザー空間のバッファに書いても、元のページキャッシュは変わりません。
しかし splice() は違います。splice() は、ユーザー空間の malloc バッファを経由せず、カーネル内部でページ参照を渡すことがあります。つまり、
/usr/bin/su の page cache
        ↓ splice()
pipe / socket / AF_ALG 側へページ参照として渡る
という感じです。
ここで「持ち込まれる」と言っても、ファイル内容が新しい安全なコピーに移るという意味ではありません。より正確には、「このデータはこのpage cache pageにあります」という参照が、カーネル内部のパイプやAF_ALG側へ渡る、ということです。
カーネル暗号APIでは、このようなページ群を scatterlist として扱います。scatterlist は、データがメモリ上のどのページのどの範囲にあるかを表すリストです。
たとえば概念的には、
scatterlist
  [page A, offset 100, length 300]
  [page B, offset 0,   length 4096]
  [page C, offset 20,  length 1000]
みたいなものです。
だから今回、splice() で /usr/bin/su の内容をAF_ALG側に渡すと、AF_ALGの入力側 req.src は概念的にこうなります。
req.src
  → /usr/bin/su の page cache page を指す scatterlist
ここで algif_aead のin-place処理が問題になります。
普通なら、暗号処理のrequestには、
src = 入力として読む場所
dst = 出力として書く場所
があります。
安全な out-of-place 処理なら、
src = 入力データ
dst = 別の安全な出力バッファ
です。
つまり、
src != dst
です。
一方、in-place 処理では、
src と dst が同じ場所を指す
ことになります。これは、同じバッファを読んで、同じバッファに結果を書き戻す形です。普通の作業用メモリなら、コピーを減らすためにありえる最適化です。
でも今回まずかったのは、src が普通の作業用メモリではなく、splice() 由来のページキャッシュだったことです。
概念的にはこうです。
req.src = /usr/bin/su の page cache を指す scatterlist
ここで algif_aead が in-place にしてしまうと、
req.dst = req.src
に近い状態になります。
つまり、
req.src
  → /usr/bin/su の page cache

req.dst
  → /usr/bin/su の page cache
になってしまいます。
ここで出てくる buf という表現は、実在する malloc バッファのことではありません。src と dst が同じ実体を指している状態を説明するための抽象名です。今回の実体は、ユーザー空間の char *buf ではなく、scatterlist が指しているページキャッシュ上のページです。
つまり、
buf = mallocされた普通のバッファ
ではなく、
src/dst が同じ page cache page を指している状態
という意味です。
その状態で、実際の暗号エンジンである authencesn が動きます。
authencesn には、ESN、つまりExtended Sequence Number関連の処理があります。その中で hiseq という4バイト値を扱います。hiseq は high-order sequence bits のような値で、認証計算に使われるものです。
古い実装では、この hiseq を dst の末尾側に置く処理がありました。ここがかなり設計的に危ないところです。
authencesn 目線では、おそらく、
dst は暗号処理用の出力・作業領域である
だから dst の末尾側に hiseq 4バイトを置いてもよい
という前提だったのだと思います。
でも、この前提はかなり危ういです。普通に考えれば、dst に書いてよいのは、呼び出し側が「ここは出力用に確保済み」と保証した範囲だけです。dst の末尾を作業場所として使うなら、その4バイトが本当に確保済みで、かつ書いてよい領域であるという契約が必要です。
だから、僕目線でも authencesn はかなり悪く見えます。dst の末尾を勝手に hiseq の置き場にする設計は、単体で見ても危ないです。
ただし、今回それがページキャッシュ破壊として爆発した理由は、algif_aead が in-place によって dst を src と重ね、その src が splice() 由来のページキャッシュだったからです。
つまり流れはこうです。
splice()
  → /usr/bin/su の page cache page を req.src に持ち込む

algif_aead
  → in-place 処理で req.dst も req.src と同じものにする

authencesn
  → req.dst に hiseq 4バイトを書く

結果
  → req.dst は page cache を指していたので、
     /usr/bin/su の page cache に4バイト書かれる
ここで重要なのは、authencesn が「/usr/bin/su を書き換えよう」としているわけではないことです。authencesn から見ると、ただ dst に hiseq 4バイトを書いただけです。しかし、その dst が実はページキャッシュを指していたため、結果としてページキャッシュが書き換わります。
つまり今回の脆弱性は、
ページキャッシュを普通に write() した
のではなく、
ページキャッシュ由来の入力を、暗号処理の出力先 dst としても扱ってしまった
ことが本質です。
通常のファイル書き込み経路なら、
このファイルに書き込み権限があるか？
このfdは O_RDONLY ではないか？
みたいなチェックがあります。
でも今回の書き込みは、通常のVFS write経路ではありません。カーネル暗号処理の内部から見ると、
暗号処理の dst に4バイト書く
という動きです。
その dst がページキャッシュだったので、ファイル書き込み権限チェックを通らずに、ページキャッシュ側だけが変わってしまうわけです。
AF_ALGの処理結果は recv(opfd, ...) で受け取ります。recv は receive、つまり受け取るという意味です。AF_ALGでは、暗号処理の結果を受け取る操作になります。
AEADでは、認証に失敗すると recv() はエラーを返します。本来なら、
認証失敗
  → 何も反映しない
  → エラーを返す
であるべきです。
でも今回の問題では、
処理途中で authencesn が dst に hiseq 4バイトを書く
        ↓
その後で認証失敗になる
        ↓
recv() はエラーを返す
        ↓
でも4バイトの副作用は page cache に残る
という構造になります。
つまり、「エラーが返るから安全」ではありません。エラーを返す前に、すでに副作用が出てしまっているのが問題です。
一方、コード中の sc[] はshellcode的なバイト列を表すものとします。sc は shellcode の略としてよく使われます。これを一気に扱うのではなく、memcpy(&val, sc + i * 4, nbytes) で4バイトずつ val にコピーします。
memcpy は memory copy の略で、メモリ上のある場所から別の場所へ指定バイト数だけコピーする関数です。sc + i * 4 は、sc の先頭から i * 4 バイト進んだ位置を表します。つまり、i 番目の4バイト塊を取り出しています。
その4バイト値 val を、
do_write(algfd, tgtfd, entry_foff + i * 4, val)
に渡します。
ここでの do_write は普通の write() ではありません。名前はwriteっぽいですが、実際には AF_ALG、accept()、sendmsg()、splice()、recv() などを組み合わせて、指定したファイルオフセットに対応するページキャッシュ側への副作用を狙う処理です。
第1引数 algfd はAF_ALGの親ソケット、第2引数 tgtfd は対象ファイル /usr/bin/su のfd、第3引数 entry_foff + i * 4 は反映を狙うファイル上の位置、第4引数 val は今回扱う4バイト値です。
entry_foff は実行開始地点のファイルオフセットです。そこに i * 4 を足すことで、4バイトずつ位置を進めています。
つまり、概念的には、
entry_foff + 0
entry_foff + 4
entry_foff + 8
entry_foff + 12
...
という位置に、sc[] の内容を4バイト単位で並べていくことを狙っています。
最後に、execl(TARGET, TARGET, NULL) で /usr/bin/su を実行します。
exec は、現在のプロセスを別のプログラムで置き換える操作です。execl の l は list で、引数をリスト形式で渡すという意味です。
第1引数の TARGET は実行するプログラムのパス、第2引数の TARGET は argv[0]、つまりプログラム自身の名前として渡される文字列、最後の NULL は引数リストの終端です。
execl() が成功すると、元のPoCプログラムのプロセスは /usr/bin/su に置き換わります。このとき、カーネルは /usr/bin/su を実行するためにファイル内容を読み込みます。その読み込みにはページキャッシュが関係します。
だから、直前の処理でページキャッシュ上の実行開始地点付近が本来と違う内容に見える状態になっていれば、本来とは違う命令列が実行される可能性があります。
